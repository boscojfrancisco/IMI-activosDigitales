# Identidad central para Activos Digitales

Esta copia es candidata y no se ha publicado. El tablero usa conexiones separadas a `imi_identidad` y `imi_activos_digitales`, ambas con TLS y certificado verificado. No copiar contraseñas ni claves al repositorio.

El servidor lee `.env.integrado.local` desde el directorio de la aplicación. Debe contener `IMI_INTEGRACION=si`, `IDENTIDAD_HOST`, `IDENTIDAD_PORT`, `IDENTIDAD_DATABASE`, `IDENTIDAD_USER`, `IDENTIDAD_PASSWORD`, `IDENTIDAD_CA`, `DATOS_HOST`, `DATOS_PORT`, `DATOS_DATABASE`, `DATOS_USER`, `DATOS_PASSWORD`, `DATOS_CA` y `PILOTO_JWT_SECRET`; los valores de base esperados son `imi_identidad` e `imi_activos_digitales`. Las rutas CA deben apuntar a certificados confiables presentes en el servidor. La clave de sesiones debe ser aleatoria, estable y de al menos 48 caracteres. Proteger el archivo y las claves con permisos del usuario de servicio y respaldarlas según el procedimiento operativo. `VITE_BASE_PATH=/imi-activos/` permanece en la configuración de compilación del tablero.

Por defecto se bloquean las operaciones HTTP de modificación y se solicita que las transacciones de datos sean de solo lectura. La autenticación puede actualizar límites de intentos y credenciales legadas en la base de identidad. Para el corte, `IMI_SOLO_LECTURA=no` habilita las operaciones del tablero y `IMI_CONGELAR_IDENTIDAD=si` pausa altas, cambios de contraseña y cambios de permisos mientras se observa el sistema. Esta pausa se probó con PostgreSQL local; no impide cambios en las bases desde otras aplicaciones o herramientas. El bloqueo de aplicación no reemplaza un rol PostgreSQL con privilegios mínimos.

El rol de identidad y su regla TLS se prepararon para la dirección del servidor y se verificaron desde allí. El rol no puede actualizar `es_admin_global`, emitir invitaciones iniciales ni borrar auditoría. `permisos-identidad-plantilla.sql` documenta los privilegios ensayados; no crea roles ni configura la red. El alta inicial web solo está disponible en el modo explícito de prueba local; la cuenta administradora ya se preparó por separado. El archivo protegido de configuración del servidor ya está preparado en modo de verificación y todavía no lo usa el tablero publicado.

También se preparó un rol específico para los datos del tablero, sin privilegios de superusuario ni lectura de la tabla antigua de usuarios. Se ensayaron sus permisos sobre una copia restaurada y se comprobó su conexión TLS desde el servidor. La aplicación anterior sigue utilizando su configuración original hasta el corte; la credencial histórica debe rotarse coordinadamente cuando se hayan identificado todos sus consumidores y se haya preparado la reversión.

La cuenta administradora antigua ya se vinculó con su identidad central; se conservó el historial del tablero y la copia anterior permanece inactiva. Las demás cuentas ya se activaron en identidad después de comprobar los estados y rangos. El tablero publicado aún usa la base anterior: congelar cambios de usuarios y volver a comprobar el origen antes del corte. La reversión debe contemplar cambios de usuarios y contraseñas posteriores al corte; volver solo la aplicación a la versión anterior no los sincroniza automáticamente.

## Primer corte supervisado

El coordinador `corte-activos.cjs` y el runner intercambian una confirmación antes de finalizar. El coordinador bloquea las tablas de identidad y de usuarios legados, comprueba huellas, correspondencias, estados y rangos antes y después del arranque y supervisa ambas conexiones. Si una verificación falla o el coordinador desaparece antes de confirmar, el supervisor detiene el despliegue y el runner intenta restaurar la versión anterior. En una prueba descartable se ensayaron el éxito, el rechazo, la pérdida de conexión y la caída del coordinador con el runner y comandos simulados.

El coordinador requiere una copia revisada fuera del directorio que el runner cambia, con sus dependencias, y que el runner instalado coincida exactamente con el incluido en esa copia. Recibe por `IMI_CORTE_CONFIG` la ruta de un JSON propiedad del usuario de servicio y con modo 600, con `source` y `target` (cada uno con `host`, `port` numérico, `database`, `user`, `password`), `caFile` y `keyFile`; la clave HMAC también debe tener modo 600 y pertenecer al usuario de servicio. Los destinos remotos usan TLS verificado. El archivo de configuración integrado del tablero debe tener habilitadas las escrituras de negocio y congelados los cambios de identidad. No guardar secretos en Git.

La coordinación no es una transacción distribuida: una caída o pérdida de conexión justo después de confirmar el cambio puede dejar un resultado incierto. En ese caso se debe comprobar qué versión quedó en ejecución y conciliar el origen antes de actuar. El mecanismo no reemplaza respaldos recientes, comprobación de restauración, acceso de contingencia ni seguimiento del despliegue. No levantar la congelación hasta tener un procedimiento probado para conciliar contraseñas y permisos en caso de reversión.
